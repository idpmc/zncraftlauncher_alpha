# ZNCraftLauncher 发布与安装说明

> 版本号唯一来源是 `package.json` 的 `version` 字段。改版本号只需要改那一处。

## 一、为什么安装包会被 Windows 拦下

**结论：安装包没有数字签名。** 这是Windows 的策略，不是打包出错。

SmartScreen 对可执行文件的判断分四档（微软官方口径）：

| 情况 | 首次下载时的表现 |
|---|---|
| Microsoft Store | 无提示 |
| 已签名的 OV/EV | 软警告，显示已验证的发行者名字，可直接点「运行」；信誉逐步累积 |
| **无签名** | **蓝窗「Windows 已保护你的电脑」，只有「不运行」**，必须点「更多信息 → 仍要运行」 |
| 自签名 | **与无签名完全相同** |

两个容易踩空的认知：

1. **自签名证书没用。** 它和不签名在 SmartScreen 眼里是同一档，不要用「自己签一个」来糊弄。
2. **EV 证书不值。** 微软 2024 年 8 月起取消了 EV 的即时信誉授予，EV 和 OV 现在走同一套累积流程。**只为躲 SmartScreen 而买 EV 不划算**，OV 足够。

本项目的两个包当前都是 `NotSigned`（可用 `npm run verify:signature` 随时复核）。

## 二、用户侧临时绕过

按顺序试，任一成功即可。每台机器只需做一次。

**方法 1 — 解除锁定（最快）**

右键 `ZNCraftLauncher-<版本>-Setup.exe` → 属性 → 最下方勾选「解除锁定」→ 确定 → 再双击。

**方法 2 — 命令解除标记**

```powershell
Unblock-File -Path .\ZNCraftLauncher-0.3.23-alpha-Setup.exe
```

**方法 3 — 点进去强跑**

蓝窗里点「更多信息」→「仍要运行」。

### 如果方法 1–3 都无效

那就不是 SmartScreen。**SmartScreen 的文案是「Windows 已保护你的电脑」并且一定有
「更多信息 → 仍要运行」**。如果弹窗文案是别的（比如「无法识别的软件」、
「智能应用控制已阻止可能不安全的应用」），说明是更下面的一层。

这一层的特征是**没有「仍要运行」**，`Unblock-File` 也无效 —— 它在内核级
（WDAC / Device Guard）拦截，进程根本没启动，安装器内部任何逻辑都跑不到。

### 三层拦截的判定方法

| 层 | 弹窗文案 | 有「仍要运行」吗 | `Unblock-File` 有用吗 | 留日志吗 |
|---|---|---|---|---|
| SmartScreen | Windows 已保护你的电脑 | **有** | 有 | 不留 |
| 智能应用控制 SAC | 无法识别的软件 / 已阻止可能不安全的应用 | **没有** | **无效** | CodeIntegrity **3077** |
| AppLocker / WDAC（企业） | 已被组织策略禁止 | 没有 | 无效 | AppLocker **8004** |

**先跑这个命令确认 SAC 状态：**

```powershell
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy' `
  -Name VerifiedAndReputablePolicyState |
  Select-Object VerifiedAndReputablePolicyState
```

`0` = 已关闭，`1` = 评估模式（暂不拦），`2` = 已开启（**会硬拦**）。

**再看硬拦日志（SmartScreen 拦截不会有记录）：**

```powershell
Get-WinEvent -LogName 'Microsoft-Windows-CodeIntegrity/Operational' -MaxEvents 10 |
  Select-Object TimeCreated, Id, Message | Format-List
```

有 **ID 3077** 就是 SAC/WDAC 拦的。

仓库里的 `release\诊断-安装被拦截.ps1` 把上面这些一次性查完并输出
`拦截诊断结果.txt`，连同安装包签名状态、Defender 状态、第三方杀毒一起。

### 关掉智能应用控制

```
设置 → 隐私和安全性 → Windows 安全 → 应用和浏览器控制 → 智能应用控制 → 关闭
```

⚠️ **关闭后无法重新开启** —— 当前版本要重开只能「重置此电脑」。
所以对最终用户来说这不是可接受的方案。

### 结论：为什么代码签名从「锦上添花」变成「必需品」

微软官方对 SAC 判定逻辑的说明：

> 如果安全服务无法对应用做出可靠的预测，则智能应用控制会检查应用是否具有
> **有效的签名**。如果应用具有有效的签名，智能应用控制将允许它运行。
> 如果应用未签名或签名无效，则将其视为不受信任并**阻止**。

也就是说：

- 签名能让 SAC **放行**，而不只是「把警告变软」
- 微软明确说明 **无法为单个应用绕过** SAC，只能关掉它或签名
- 买 OV 证书（约 $109–129/年）是唯一能让普通用户在默认 Windows 11 上
  正常安装的办法

所以 `npm run package:signed` 不是「以后再说」的优化项，而是分发渠道的
前置条件。详见下一节。

### 免安装方式

不想跟这些机制较劲，直接用免安装版：

```
release\win-unpacked\
```

整目录拷过去运行 `ZNCraftLauncher.exe` 即可，不经过安装器。

## 三、配置代码签名

### 需要什么

一张 **OV 代码签名证书**，必须含私钥（PFX / P12 格式）。参考价位：SSL.com 约 $109–129/年（含云签名，无需 USB key；淘宝/阿里云等代理渠道价格会不同）。

采购时的验收要点：

- 类型必须是 **Code Signing**，OID `1.3.6.1.5.5.7.3.3`
- 问清**是否含私钥交付**，以及交付形式（`.pfx` 文件 / 云签名账号）
- 有效期上限 460 天（CA/Browser Forum 规定），到期前需续签
- **不需要** EV

### 配置步骤

密码走环境变量，**不要写进 `package.json`，不要提交进仓库**。

```powershell
# 仅本次生效
$env:CSC_LINK = "D:\certs\zncl.pfx"
$env:CSC_KEY_PASSWORD = "<证书密码>"

# 或永久生效（setx 只对「新开的」终端生效，需重开终端）
setx CSC_LINK "D:\certs\zncl.pfx"
setx CSC_KEY_PASSWORD "<证书密码>"
```

然后打包：

```powershell
npm run package:signed
npm run verify:signature
```

`package:signed` 会在开跑前检查证书，缺失就报错退出。**不用它也可以** —— 直接 `npm run package` 在环境变量就绪时同样会签名；但那个组合下漏检会静默通过，而「以为签了其实没签」是最难发现的错误，所以建议统一走 `package:signed`。

`verify:signature` 会同时检查安装包和 `win-unpacked` 下所有 exe 的签名状态、时间戳和 SHA256。

### 已配置的打包参数

`package.json` → `build.win`：

```json
"signingHashAlgorithms": ["sha256"],
"rfc3161TimeStampServer": "http://timestamp.digicert.com",
"verifyUpdateCodeSignature": false
```

时间戳很重要：证书到期后，只要签名时打了时间戳，签名依然有效。

### `signAndEditExecutable: false` 为什么必须保留

**它同时控制签名和 exe 资源编辑（图标、版本信息）。**设为 `false` 时
`app-builder-lib/out/winPackager.js` 的 `signApp()` 直接 `return false`，
**无论有没有证书都不会签名** —— 所以 `package:signed` 必须用
`--config.win.signAndEditExecutable=true` 在命令行把它打开。

而它**不能直接从配置文件里删掉**，原因不是「怕崩」：

打开后 electron-builder 需要解包 `winCodeSign`，该包内含 macOS 的符号链接：

```
ERROR: Cannot create symbolic link : 客户端没有所需的权限
        ...\winCodeSign\399937943\darwin\10.12\lib\libcrypto.dylib
Above command failed, retrying 3 more times
⨯ cannot execute  cause=exit status 2
```

非提权进程要创建符号链接，需要系统开启「开发人员模式」；否则重试 3 次后
**整包构建失败**。签名用的 `signtool.exe` 和资源编辑用的 `rcedit.exe` 都来自
这个包，所以签名机器上必须先解决权限。

`scripts/require-cert.js` 会在打包前实测符号链接能否创建，不能就报错并给出办法：

- **A** 用「以管理员身份运行」的 PowerShell 执行 `npm run package:signed`
  （提权进程自带 `SeCreateSymbolicLinkPrivilege`）
- **B** 一次性开启开发人员模式，之后普通终端即可：

```cmd
reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock" /t REG_DWORD /f /v AllowDevelopmentWithoutDevLicense /d 1
```

两条路都不走也能正常出包 —— `npm run package` 用的是 `false`，完全不碰
`winCodeSign`，只是产物没有签名。

## 四、已知行为

### 安装模式：只走「为所有用户」（`perMachine: true`）

安装路径是 `C:\Program Files\ZNCraftLauncher`，**需要管理员权限**。

**为什么这么设：** 实测只有「为所有用户安装」这条路能装成功，「仅为我安装」会失败。
两条路里只有一条能用，就不要留一个会失败的选项给用户。

源码链路：

| 位置 | 代码 |
|---|---|
| `out/targets/nsis/NsisTarget.js:412-413` | `perMachine === true` → 定义 `INSTALL_MODE_PER_ALL_USERS` |
| `templates/nsis/assistedInstaller.nsh:85-86` | `!ifdef INSTALL_MODE_PER_ALL_USERS` → `.onInit` 里立刻 `setInstallModePerAllUsers` |
| `templates/nsis/include/allowOnlyOneInstallerInstance.nsh:41` | `!ifdef INSTALL_MODE_PER_ALL_USERS` → 用 `nsProcess::FindProcess`，而非带 `USERNAME` 过滤的 tasklist |

**已验证**：同一个 `customInit` 日志钩子，两种配置下打印的 `instdir` 不同 ——

```
perMachine: false -> instdir=C:\Users\<你>\AppData\Local\Programs\ZNCraftLauncher
perMachine: true  -> instdir=C:\Program Files\ZNCraftLauncher
```

`$INSTDIR` 只在 `assistedInstaller.nsh:85-86` 那个 `!ifdef` 分支里被提前设成
Program Files，所以这行日志足以证明 define 生效、安装模式已被强制为「所有用户」。

**未验证**：选择页是否还渲染。`assistedInstaller.nsh:85` 只是提前设好模式，
页面是否仍插入要看 `MUI_PAGE_FUNCTION_INSTALL_MODE_PAGE` 的插入条件。
想确认就跑一次带调试的构建，dump 生成的 NSIS 脚本：

```powershell
$env:DEBUG = 'electron-builder'
npm run package
# 读 F:\zncl0.1.23\release\builder-debug.yml 里的 nsis.script
```

⚠️ dump 只保留**最后一次** makensis 调用，而 electron-builder 会先编卸载器
（带 `BUILD_UNINSTALLER`）再编安装器，所以最后那份**是安装器**。用
`Section "install" INSTALL_SECTION_ID` 是否存在来确认自己没读错。

需要免安装、不想要管理员权限的，走 `release\win-unpacked\`。

### 提权后的残留进程会卡死打包

实测：启动安装器向导后，用普通权限的 PowerShell 杀不掉它 —— `Stop-Process` 和
`taskkill /f /t /im` 都返回「拒绝访问」。原因是它已自提权，而 UIPI 不允许低完整性
进程操作高完整性进程（往它窗口发 `WM_CLOSE` 同样无效）。

这会连锁成打包失败。残留进程锁住 `release\win-unpacked` 里的文件时，
electron-builder 停在：

```
• output file is locked for writing (maybe by virus scanner) => waiting for unlock...
```

然后一直等到超时（本次实测卡了 15 分钟）。**打包前务必确认没有残留进程**：

```powershell
Get-Process | Where-Object { $_.ProcessName -like '*ZNCraftLauncher*' } |
  ForEach-Object { Stop-Process -Id $_.Id -Force }
```

报「拒绝访问」就只能手动关掉它的窗口，或开一个管理员终端来杀。

顺带一个已知局限（来自源码，未实测）：`installSection.nsh:35` 是
`!ifNot ${UAC_IsInnerInstance}`，所以 `customCheckAppRunning` 只在**未提权**的
实例里执行。若真正干活的实例是提权后的，这个检查根本不会跑。

### 安装器的「应用正在运行」检查已被覆盖

electron-builder 默认实现在检测和强杀进程时都带 `USERNAME eq %USERNAME%` 过滤：

```
tasklist /FI "USERNAME eq %USERNAME%" /FI "IMAGENAME eq ..." | find.exe "..."
```

安装器经 UAC 提权后，`%USERNAME%` 可能与实际运行启动器的用户不一致，于是误判成
「正在运行」，强杀又因同样的过滤杀不掉，重试超限后弹出
`$(appCannotBeClosed)` 的 Retry/Cancel —— 那个弹窗里点任何按钮都前进不了。

`build/installer.nsh` 用 `customCheckAppRunning` 覆盖了这段逻辑：

1. 只按 IMAGENAME 判断，去掉 USERNAME 过滤
2. `taskkill /f /t /im` 强杀（含子进程），每轮间隔 **1.2 秒**等句柄释放
3. 每轮复查一次，最多 **10 轮**（约 12 秒）
4. 仍关不掉则**提示但不阻塞安装**（残留进程通常不锁 `app.asar`，硬装能成功）
5. 全部过程写入 `%TEMP%\zncl-install-diagnostic.log`（见下文「诊断日志」）

验证方式：electron-builder 生成的脚本里，若 `Var pid` / `GetProcessInfo` /
`getProcessInfo.nsh` 计数均为 0，说明走的是本项目实现而非默认实现。

> 注意：`build/installer.nsh` 带 UTF-8 BOM。makensis 对被include 的文件按各自
> BOM 判定编码，缺 BOM 会按系统 ACP（中文 Windows 为 GBK）读中文注释并报
> `Bad text encoding`。改这个文件时不要用会剥掉 BOM 的方式重写。
>
> 另外不要把宏名改成 `CHECK_APP_RUNNING` —— 那是 electron-builder 自己的名字，
> 重定义会报 `macro already exists`。

### 装完不自动启动（`runAfterFinish: false`）

electron-builder 的 NSIS 默认 `runAfterFinish = true`，装完自动启动程序。这会让
**下一次安装必然失败**：启动的 `ZNCraftLauncher.exe` 锁住 `$INSTDIR` 里的文件，
而下面两个死结都由文件被锁触发。所以本项目显式关掉它，装完请从快捷方式启动。

### 同一文案有三个来源，只有第一个能覆盖

`$(appCannotBeClosed)` 在 electron-builder 模板里出现 **3 次**：

| 文件 | 行 | 场景 | `nsis.include` 能否覆盖 |
|---|---|---|---|
| `allowOnlyOneInstallerInstance.nsh` | 110 | 安装前进程检查 | **能**（`customCheckAppRunning`） |
| `extractAppPackage.nsh` | 116 | 解压写入 `$INSTDIR` 被占用 | 不能，宏体内联 |
| `installUtil.nsh` | 219 | 卸载旧版本失败 5 次 | 不能，宏体内联 |

后两处的 Retry 与 Cancel **都导向中止**，点任何按钮都前进不了，只能杀掉安装器重来。
而且 `extractAppPackage.nsh:112-114` 的 5 次重试**之间没有 `Sleep`**，是毫秒级连撞
5 下 —— 只要句柄还没释放就必弹。

安装段的执行顺序（`installSection.nsh`）：

| 行 | 阶段 |
|---|---|
| 52 / 56 | `uninstallOldVersion` ← 死结 3 |
| 66 | `installApplicationFiles` ← 死结 2 |
| 81 | `customInstall` ← 排在这两个之后 |

### 诊断日志（排查安装失败先看这个）

`build\installer.nsh` 用 `FileOpen`/`FileWrite` 写自己的日志，**不用** NSIS 的
`LogSet` —— 它要求编译期宏 `NSIS_CONFIG_LOG`，而该宏既不在 NSIS 的 `nsisconf.nsh`
里，也不在 electron-builder 传给 makensis 的 `-D` 参数里。在脚本里自己
`!define` 它无效，会报：

```
Error: LogSet specified, NSIS_CONFIG_LOG not defined.
```

日志位置（安装器与卸载器都会写，**安装失败也留痕**）：

```
%TEMP%\zncl-install-diagnostic.log
```

三个可覆盖钩子各写一个阶段标记：

| 标记 | 含义 |
|---|---|
| `INIT version=... instdir=...` | 安装开始（`customInit`） |
| `CHECK try=N exit=0/1` | 每次复查的检测结果 |
| `CHECK found ... killing (attempt N)` | 发现进程并强杀 |
| `CHECK clear, proceeding` | 无运行实例，正常继续 |
| `CHECK GAVE_UP after 10 rounds` | 杀约 12 秒仍关不掉，继续安装 |
| `EXTRACT_OK instdir=...` | **解压与卸载旧版本都已通过**（`customInstall`） |

**读法：**

- 只有 `INIT`、没有 `EXTRACT_OK` → 卡在 `uninstallOldVersion`（死结 3）
- 有 `CHECK` 但没有 `EXTRACT_OK` → 卡在 `installApplicationFiles`（死结 2）
- 有 `EXTRACT_OK` → 安装主体已完成
- **一条 `ZNCL_CHECK` 都没有** → 走的是 electron-builder 默认实现，不是本文件

写日志的宏里**不能放 label** —— NSIS 的 label 是全局的，同一宏被插入多处会报
`duplicate label`。所以 `ZNCL_LOG` 里不做 `IfErrors` 分支。

还有一条已知局限：`installSection.nsh:35` 是 `!ifNot ${UAC_IsInnerInstance}`，
本宏只在提权前的**外层实例**执行。若启动器是以管理员权限运行的，非提权的
`taskkill` 杀不掉它，会走 `GAVE_UP` 分支 —— 日志里能明确看到。

## 五、校验下载完整性

```powershell
Get-FileHash -Algorithm SHA256 -Path .\ZNCraftLauncher-<版本>-Setup.exe
```

`npm run verify:signature` 会同时输出 SHA256。
